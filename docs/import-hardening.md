# 0.2.0：重复导入问题与验证

## 问题依据

历史使用记录曾确认：同一篇文献以独立条目分散在不同分类，并非只是一个条目同时属于多个分类。Zotero 的去重范围是 library，分类不能作为再次创建条目的依据。

代码检查还发现以下可复现风险。这些是实现分析及模拟实验结果，不代表每一种都曾发生在真实文库中。

| 原行为 | 可能后果 | 0.2.0 行为 |
| --- | --- | --- |
| 默认 `q` 搜索不保证命中 DOI，摘要也省略 DOI | 把已有文献当作不存在 | 规范化 DOI/DOI URL，完整扫描后精确匹配，并返回 DOI |
| 单次列表读取没有分页完整性检查 | 第一页以外的条目被漏掉 | 分页核对总数、唯一 key 和文库版本 |
| Connector 导入直接发送全部输入 | 重复创建已有记录或批次内副本 | 先计划，跳过同 DOI 已有条目与批次内重复 |
| 每次默认生成新会话，超时后缺少持久记录 | 服务端已写入时，客户端重试仍可能再次发送 | POST 前记录 pending，结果不确定时阻止新请求 |
| 只检查 HTTP 响应 | 部分成功、响应丢失无法区分 | 回读全部待导入身份，并要求唯一的新 key |
| 多个调用同时检查“没有” | 检查与写入之间发生竞态 | 同一服务地址的进程间文件锁覆盖预检和验证 |
| 导入依赖 UI 当前目标 | 分类变化导致归属不符合预期 | 写入前复查；检测到写入后变化时返回单独警告 |
| selected-target 包含完整标签清单 | 输出过长，难以定位导入目标 | 仅返回文库/分类身份和可编辑状态 |

原始 `zotero.py` 与整个上游副本保持不变。新增适配层被 Node 启动器默认使用；直接调用上游 helper 不会获得这些检查。

## 验证方法

`npm test` 包含 Node 适配测试和 Python 黑盒 HTTP/CLI 场景。后者使用随机 loopback 端口、临时状态目录和合成条目，不连接真实 Zotero。

覆盖：100 条之后的 DOI 命中、不同分类已有条目、分页截断/总数缺失/版本变化、预印本与正式版身份冲突、批次重复与部分成功、响应丢失后回读恢复、持久 pending 对新进程/新输入的阻止、并发进程互斥、进程被终止后锁释放但 pending 保留、延迟完成后的状态恢复，以及元数据解析与目标变化。

真实文库只执行了搜索、只读导入预览与候选重复报告，未执行新建、合并、删除或分类修改。正式写入、实际 DSH 模型对话及 macOS 仍需另行验收。

## 保留边界

- 标题候选不是自动合并结论；DOI 冲突不靠模糊匹配掩盖。
- 已有条目返回 key；要放入另一分类应复用该条目，而不是重新导入。
- Word 引用关系和原生合并不由这个插件改写；Zotero 官方说明原生合并会保留分类/标签并由文字处理插件识别。
- 无法对第三方软件的并发导入或 Connector 的 UI 目标切换提供全局事务保证。

官方依据：[Duplicate Detection](https://www.zotero.org/support/duplicate_detection)、[Connector 导入源码](https://github.com/zotero/zotero/blob/main/chrome/content/zotero/xpcom/server/server_connector.js)。
